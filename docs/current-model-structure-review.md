# 現行モデルの処理フローと秘密履歴の設計レビュー

調査基準は HEAD `eb8116d`。機能・意味論を変更しない読み取り中心の調査である。
調査中はHEADと実装ファイルを保持し、調査完了後にこの文書だけをcommitした。

## 最初に分かったこと

「GJを扱うには新しい履歴配分ルールが必要」と一般化するのは適切ではない。
護衛の物理的な成否は既存の役職候補、合法対象、均等護衛だけで計算できる。
問題は、**同じ公開盤面でも狼が知っていることが違い、次の襲撃政策が変わる**点である。

根から未来を計算するなら、既存の分岐列挙でその知識の獲得も伝播できる。
実現しない世界を物理的な枝に戻すための補完は、そこでの物理法則としては不要である。
一方、途中の公開Boardだけから評価を再開すると、過去に失われた他者の知識状態までは
役職候補の再列挙から一意に復元できない。配分の要求はこの再開経路と状態の契約に由来する。

現コードは物理枝と公開信念を既に一部分離している。ただし公開評価・政策の候補採点では
公開の `s` を物理分岐の入力としても使い直す。そのため、変数を二つに分けるだけでは
「公開役職分布から他者の秘密履歴まで再生成する」という構造は解消していない。

## 1. 何を表しているデータなのか

| データ | 内容と生成元 | 役割 |
|---|---|---|
| `Board` | 生存者、日・昼夜、死亡履歴、CO、公開結果、役職候補と重み | 公開情報だけを持つ盤面。私有の護衛・襲撃先は持たない |
| `Board.worlds` | `(wolf_mask, medium_mask, seer_mask, hunter_mask, mass)` | 公開情報に整合する役職世界。実役職を一つ選んではいない |
| `Hypothesis` | 役職マスク、占い取得記録、`mass`、`guards`、`attacks` | 同じ役職世界を、私有情報・行動履歴の違いで分けられる列挙行 |
| `TrueScanState` | 仮説行の集合、各夜の元の名簿、取得規則など | 占い用に始まった構造を狩人・襲撃履歴にも拡張。公開用と物理用が同じ型 |
| `PrivateView` | 公開Boardに本人条件を加えたBoard、役職・本人ID、入力した私有記録 | 視点画面の追加条件。公開盤面を変更しない |
| `GuardContext` | `public`, `private`, `public_state` | 一つの夜結果に、公開盤面と物理枝の本人分布を別々に付ける |
| `GuardHistoryMixture` | 外部の公開役職質量、公開用混合、物理混合、支持情報 | `eb8116d` の補助インターフェース。一般の政策求解器ではない |

参照: `exact.py:232`, `seer_acquisition.py:42`, `seer_future_uniform.py:17`,
`private_view.py:13`, `guard_model.py:64`, `guard_history_mixture.py:15`。

ここでの「物理分布」は、シミュレーション内で各候補世界を真と置いた場合の分岐確率である。
アプリが実ゲームの役職を一つ抽選して確定しているという意味ではない。

## 2. 入力から次の昼夜までの現行フロー

### 公開Boardと役職候補

1. `app.replay` / `structural_replay` は、保存された公開入力・履歴を再生する。
   初期配役から `initial_board` が役職の組合せを列挙し、初期COには
   `group_initial_board` のグループ共同分布を適用する。
2. `condition_claims`、公開結果、処刑・夜の観測が候補を絞り、残る重みを正規化する。
   毎回すべての役職候補を一様に戻す処理ではない。
3. `prepare_public_prior` は現在の `Board.worlds` を基に評価用 `TrueScanState` を作る。
   狩人だけの経路では `from_board` が役職と重みをコピーし、私有記録は空にする。
   占いの公開取得情報が必要なら `public_observed_prior.prepare_game` が再構築する。
   **一般の過去護衛・襲撃の同時分布はここでは再生していない。**

参照: `app.py:63/92`, `exact.py:405/176/129`, `public_prior.py:38`,
`public_observed_prior.py:10`, `seer_acquisition.py:82`。

### 本人の条件と、誰がどの行動を選ぶか

4. 私有視点は `condition_private` で、狼の初期仲間集合、本人役職、本人の取得結果・
   護衛先・襲撃先を追加条件にする。GJ時の狼の噛み先は「そこが狩人ではない」を条件にし、
   狩人の護衛先は「そこが狼ではない」を条件にする。専用の成功通知は追加しない。
5. 昼の `score_day_targets` は公開 `s` だけで候補を比較する。昼は個々人の投票ではなく、
   一つの公開処刑方針である。私有視点を選んでもその公開方針は変更しない。
6. 夜の `wolf_policy` は `(公開状態, 初期狼マスク, 狼の襲撃履歴)` を情報集合のキーにする。
   同じ狼情報集合で候補をまとめて評価し、村勝率が最小の襲撃を選ぶ。同率は均等化する。
   真の狩人位置が分かった世界ごとに別々の全知最適化をしてはいけない。
7. 狩人の将来の政策は、本人以外の生存者を均等に護衛する。視点画面の候補比較だけは、
   `GuardObserver` で現在の護衛先を固定する。その固定を狼の政策入力に渡さない。

参照: `private_view.py:23`, `private_adapter.py:47`,
`information_set_forecast.py:249/285`, `guard_model.py:47`, `guard_view_forecast.py:14`。

注意: 表示用の本人役職確率は `PrivateView.board` の重みで作るが、
`InformationSetForecast.evaluate` と `guard_forecast` はそのBoardの役職支持を主に使い、
最終評価の重みは `s.hypotheses` の条件付けから作る。二つの重みが常に同じだとは
コード上保証されていない。一般化の際に検証すべき接続点である。

### 物理結果、公開更新、再帰

8. `uncached_act` が `private.public_roles` から物理計算用Boardを作り、共通の
   `action_flow` / `resolve_action` に渡す。夜は能力取得を死亡より先に処理する。
9. `guarded_outcomes` は各仮説の真の狩人を物理効果のために参照し、均等護衛を列挙する。
   噛み先と護衛先が一致した枝を無死亡とし、仮説に両者の実際の行動記録を追加する。
   同じ結果の枝の質量を足したものが `FlowOutcome.probability` になる。
10. 公開Boardは別に更新する。夜の死体には襲撃対象の合法性と、設定済みの均等護衛の
    失敗確率を使う。例えば護衛可能な対象の死亡には `(N-2)/(N-1)` の係数がある。
    「整合性条件付け」は全箇所が単なる0/1の除外という意味ではない。
    **狼の最適政策がその対象を選びやすい確率は公開役職更新に掛けない。**
    無死亡なら生存狩人が必要だが、非公開の実際の噛み先を公開Boardに書き込まない。
11. `InformationSetActionPolicy.project` は、公開側 `st` と、実際の枝の `own` を別々に渡す。
    勝者が決まれば終了。未決なら朝の公開結果処理を通り、`solve` が次の昼夜を評価する。
    夜の実際の期待値は `own` を狼情報集合ごとにまとめ、同じ情報集合の政策を適用して足す。

参照: `information_set_forecast.py:227/396/311`, `action_flow.py:38/52`,
`guard_model.py:95/71`, `phase_updates.py:23`, `dawn.py:61`。

## 3. 三種類の分布・記録を混ぜない

| 種類 | 生成・用途 | 重要な境界 |
|---|---|---|
| 実際の分岐確率として使う分布 | `private`, `GuardContext.private`、夜の `mass × 護衛確率`、新インターフェースの `physical` | 実現可能な役職・本人情報・行動の同時分布。条件付き物理確率には政策が含まれ得る |
| 公開方針の評価が採用する分布 | `Board.worlds`, 公開 `s`, 新インターフェースの `public` | model Aの役職重みを所有。非公開政策の尤度による役職推測は追加しない |
| 本人が知っている記録 | `PrivateView.guards/attacks/acquisitions`、各仮説の履歴 | 一人・一陣営の事実。全プレイヤーへ公開したり、未知の私有情報を知っていることにしない |

`Hypothesis.mass` の名前だけでは、上のどの分布に属するか判別できない。
また、物理分布を本人の事実で条件付けた統計的分布と、model Aの公開信念に本人条件を
加えた主観分布が常に等しいとは限らない。新インターフェースの `_owner_view` は前者であり、
既存 `condition_private` は後者に近い整合性投影である。名称だけで両者を置換すべきではない。

支持ありの既存テストでも、公開用の世界内正規化分布を直接条件付けると `5/7:2/7`、
物理分布の本人条件付けは `2/3:1/3` となる。これは新しい確率を正解として採用したというより、
二つの質問に対する分布が異なることの検証である。

| 箇所 | HEAD eb8116dで実際に行うこと |

復旧後の修正で除かれている。それでも「再評価用の新しい仮説をBoardから作る」入口は残る。

## 4. 分離済みなのに残っている再投入経路

具体的なコードは次の通り。

```text
scalar(b, s, past) -> solve(b, s, past, private=s, observer=None)
score_day_targets  -> act(b, s, past, target, private=s, observer=None)
wolf_policy       -> public s を狼マスク・本人履歴で絞った group -> act(... private=group)
uncached_act      -> replace_worlds(b, private.public_roles) -> action_flow(...)
```

この候補評価では、公開信念から物理的な未来分岐を再生成する。
一方、既に発生した物理枝の再帰では `GuardContext.private -> own -> solve(... own ...)`
が残るため、**すべての再帰で物理分布を無条件に捨てているわけでもない**。

`eb8116d` の `extend_success` は `GuardHistoryMixture` を作るが、返すのは `.public` だけ。
`.physical` を根から全評価へ持ち回る一般的な実行経路にはなっていない。
公開候補採点と実際の分岐期待値が同じsolver・同じ状態型を使う構造はそのままである。

公開用 `s` には `s.public_roles == Board.worlds` の強い契約がある。
最適政策ではGJを起こせない役職世界をmodel Aの公開Boardが残すと、物理履歴だけでは
その契約を満たす公開用の完全な同時分布が作れない。この「ゼロ支持への配分」の要求は、
ゲームの護衛規則ではなく、この完全な再生成を要求する設計との衝突である。

実際の根からの物理枝は、その世界が観測を起こせないなら枝の確率が0でよい。
公開方針が保持する主観的な役職候補へ戻すために、それを物理枝へ復活させる必要はない。
ただし公開の最終勝率最大化が**どの情報状態・どの測度で将来の他者政策を採点するのか**は
別の契約である。物理分布を公開の採点にそのまま使えば、間接的に政策尤度による推測を
取り入れる可能性がある。二変数に分けるだけでその意味論まで自動的に決まるとは言えない。

## 5. 根からの未来計算と、途中Boardの再計算を分ける

| 経路 | 入力にある情報 | できること／不足すること |
|---|---|---|
| 根からの未来分岐 | 初期世界、選ばれた方針、各枝の行動・観測 | 私有情報が生まれる瞬間を列挙でき、同じ狼情報集合を束ねて政策を選び、その物理質量を伝播できる。新しい仮履歴の補完を物理法則へ追加する必要はない |
| 現行の画面再計算・手動編集 | 公開入力をreplayした現在Board、公開結果、元の名簿。私有視点なら本人が入力した記録 | 現在役職候補と本人条件は作れる。他者の過去私有情報の分布は、一般にはこのBoardだけでは一意でない |
| 途中Boardを根から再導出 | 過去の公開入力と方針を使った情報集合付きreplay | 既存のreplayを拡張・共通化する案。編集・戻る後も再生できる。ただし物理支持がない公開編集を「元の方針どおり起きた枝」とみなすことはできない |
| 途中Boardを独立したwhat-if開始点にする | 任意の公開候補と、本人条件・必要な情報状態 | 過去が未来に無関係ならBoardだけでよい。過去が政策に関係するなら実履歴入力、伝播済み情報状態、または明示した開始モデルが必要 |

`app.replay` は公開の役職Boardを再生するが、全狼情報集合を含む物理同時分布を
一般に再生してはいない。`public_history_key` も全過去政策を独立の履歴入力としては保持せず、
Boardと公開取得情報に依存する。現在の対応範囲外の一般履歴まで同一キャッシュで再現できると
解釈すべきではない。これは将来の設計上の依存関係であり、今回キャッシュを変更していない。

## 6. 既存例で、役職だけでは足りないことを確認

既存テスト `test_guard_max_history` の例を読み取り診断で再確認した。
5人・狼1・狩人1・村人3で、5を処刑、4人生存の夜にGJ、翌日4を処刑。
現在は同じ公開Boardで、生存者は `(1,2,3)`。狼本人が1であるとする。

| 狼が覚えているGJ時の噛み先 | 狼が追加で知る事実 | 現コードの次の襲撃政策 |
|---|---|---|
| 2 | 2は狩人ではない | 3を襲撃 |
| 3 | 3は狩人ではない | 2を襲撃 |
| 4 | 4は狩人ではない。4は既に処刑 | 2・3を各1/2で襲撃 |

これは同じ公開Board・同じ初期狼集合に対して異なる政策であり、
`condition_private` に本人履歴を追加条件として入れる既存の仕組みで表現できる。
**特定の狼視点を計算するだけなら、未知の本人履歴を勝手に配分する必要はない。**

公開評価では、狼がどの情報集合にいるかが未知である。例えば真の役職を狼1・狩人3と
置いた物理枝では、過去GJの噛み先2も4も可能。上表の政策を固定すると、前者は次に3を
噛むため護衛では止まらず、後者は確率1/2で2を噛み、均等護衛がそれを止める確率は1/2。
この役職世界内で二つの知識状態を混ぜる後者の条件付き比率を `λ` とすれば、
次の夜の阻止確率は `λ/4` になる。
`λ` は新しいルールとして与える値ではなく、根からの分岐ならそこで導出する質量である。
途中の役職候補だけに縮めてしまうと、この質量も知識状態もなくなる。

重要なのは生の履歴文字列を必ず持ち続けることではなく、**将来政策を変える情報集合を
同じものとして潰さないこと**である。役職候補を拡張して情報状態も列挙する共通構造が候補になる。

## 7. 狩人の過去護衛を何のために残すのか

現範囲の `guard_targets` は過去対象を使わず、本人以外の生存者だけを返す。
`guard_choices` は毎夜同じ均等法を使う。連続護衛ありなので、過去の護衛対象は
次の合法対象・抽選重みを変えない。昼も公開処刑方針であり、狩人本人の個別投票政策はない。

したがって、**将来の均等護衛を生成するために過去の護衛列が必要なわけではない**。
残す用途は分けるべきである。

- 視点入力の真実性と元の夜名簿の検証、画面の編集・戻る・再表示。
- GJ夜の本人護衛先から「そこは非狼」と分かる本人の候補条件。
  `condition_private` は実際にこの条件を使っている。
- 一人の狩人・一つの襲撃でGJなら、狩人のその護衛先と狼の噛み先は一致する。
  専用の成功通知がなくても、公開の無死亡と本人行動からこの関係を導ける。
  私有視点で他者の未来政策を予測する際、これが狼の知識状態との相関を表す場合がある。

「役職候補を絞ったら護衛履歴は全部捨ててよい」とも、
「将来の均等護衛のために全生履歴を必ず持つ」とも断定できない。
公開評価だけなら、狼に残るGJ由来の非狩人情報が主要な将来依存である。
本人視点では非狼条件と他者情報集合との相関を検討する必要がある。
生履歴を保存用に残し、評価にはそれらの十分な情報要約だけを使う整理案が考えられる。

## 8. 既存の共通仕組みを再利用する整理案

| 案 | 既存から再利用するもの | 必要な整理・変わり得る意味論 |
|---|---|---|
| 現在役職候補＋本人だけの追加条件 | `Board.worlds`, `condition_private`, `replace_worlds`, 合法対象・均等護衛 | 現在の役職確率・特定本人の知識は共通化可能。他者の未知の知識状態に依存する公開最終評価まで役職だけで統一できるとは限らない |
| 根から情報集合を伝播 | `Hypothesis` の列挙、`action_flow`, 物理夜結果、`GuardContext`, 初期狼マスク | 物理分岐は実現支持だけを保持し、公開信念は政策の別入力にする。同じ情報集合の狼は必ず同じ政策。公開のmax採点に使う測度・目的を明確にする必要がある |
| 生履歴を情報要約へ圧縮 | 本人条件付け、元名簿検証、既存キャッシュの情報集合キー | 現範囲ではGJ噛み先の非狩人集合などが候補。生履歴は保存/UIへ分離。占い・霊能併存まで同じ要約で十分かは別検証。勝率同値は未確認 |
| 未知履歴を共通の開始モデルで再列挙 | 既存列挙・正規化のコード | 途中Boardを独立開始点にするための仮定。未知行動を均等とするなら設定済みmax政策と異なる意味論を導入する。未承認案は実装しない |

最初に整理すべき契約は「この重みは実際の物理枝か、公開方針の主観か、特定本人の信念か」と、
「根から伝播した状態か、途中Boardを新たな開始点として作った状態か」である。
役職の再列挙・追加条件・共通物理効果を使い回すことと、これらの契約を分けることは両立する。
新しい人数別例外を増やすより、この入口と役割の整理を先に行う案が妥当である。

## 9. 再帰・キャッシュを変える場合の確認点

現在の政策キーは `(b,s,past,mask,history)`、実際の値のキーは
`(b,s,past,value_law(private),observer)`。公開日の採点・朝の分岐は公開側の入力でキャッシュする。
役職・占いの縮約は狩人盤面で迂回され、max時の護衛・襲撃記録は通常キーに残る。
完了していない計算は予算超過・未対応として返し、完成値としてキャッシュしない。

情報要約へ変える場合は、「同じ役職候補だが上表の狼知識が違う」状態を同じ政策キーに
してはいけない。一方、過去の生履歴が違っても、合法行動・本人条件・他者情報集合への相関が
同じなら同じ評価キーにできる可能性がある。これは同値性を証明してから行う性能整理である。

## 調査で確定したこと／保留すること

確定: 公開Boardだけの新規評価と物理履歴を持つ継続評価は同じ入力ではない。
現在のroot/public候補採点には公開分布の物理評価への再投入が残る。
GJ由来の狼の知識は政策を変える。過去護衛は次の均等法の入力にはならない。
公開役職条件・本人条件・合法対象・物理効果には既存コードを再利用できる。

保留: 統一後の公開max採点に使う測度、途中Boardの評価開始モデル、十分な知識要約、
一般化した場合の既存勝率との同値性。現構造が最適とは仮定せず、新意味論も実装していない。
