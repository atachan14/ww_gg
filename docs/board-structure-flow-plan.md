## Step1の位置付け

以下の用語・分類・評価軸・代表例は、**比較用の土台案**。新しい内部設計、データ形式、機能追加、既存仕様の破棄を決定するものではない。既存コードに関して確認済みの事実は末尾に別記する。

### 1. 比較で使う「Board」

**Board＝ある進行地点について、何が起きており、何を入力・想定し、何を計算して見せるかをまとめて説明する単位。**

この定義は既存のPython `Board` クラスそのものではなく、画面上の1盤面を理解するための言葉。同じ公開地点でも「公開表示」と「本人条件を加えた表示」を区別する。表示を切り替えただけで公開入力やゲームの事実を変更したとは扱わない。

```text
比較対象の1盤面
  ├─ 確定：どの地点・何が既に起きたか
  ├─ 入力：公開された発言・結果・計算で仮定する方針など
  └─ 計算：その条件に基づく役職率・勝率・計算状態
              ↑
       公開／本人のどの条件で見た結果かを区別

作成 → 入力更新 → 共同候補から役職率
                    └→ 行動・結果の枝を評価 → 勝率
入力や前提が変わったら、古い計算結果のまま表示しない
```

これは比較用の最小flowであり、すべての実装が同じ順序の一本道を通るという主張ではない。役職率は全員分の配置候補から各人について集計する量。勝率は先の進行と設定済み方針を評価した別の量。

### 2. 確定／入力／計算の仮分類

| 区分 | 比較時に入れる意味 | 留意点 |
| --- | --- | --- |
| 確定情報 | 盤面の識別・進行地点・参照する前の地点・既に確定した公開事実 | 「真の役職が確定した」の意味ではない。画面上の夜明けと計算上の夜など、異なる段階表示を一語で混同しない |
| 入力情報 | CO、公開能力報告、死体観測、設定済み戦略、選択対象、本人の既知情報 | 発言と真の取得結果、観測入力と今から行う行動、公開と本人限定、仮入力と確定済みを区別する |
| 計算情報 | 役職率、盤面・候補別の勝率、朝までの値、累積値、Pendingや入力エラー | 何の入力・地点・視点・戦略に対応する結果かを追える必要がある。すべてを一つの「勝率」にしない |

ログは単なる計算結果ではなく、入力の所属・公開時点・変更や撤回の経緯を表す。どの区分の下へどの形で置くかはStep3以降で比較する。

同様に「視点」は公開事実そのものと区別すべき比較条件であり、新しい保存項目として置く場所を今回は決めない。Game設定と盤面ごとの設定の境界、親から継承するものと当該盤面で加わるものも、分類だけで解決したことにしない。

**simpleBoardDataは理解・比較の表現。単一オブジェクトへの保存、計算結果の永続化、関数構成やキャッシュ方式は未選定。**

### 4. 守る振る舞いと、固定しないもの

比較では以下を守る基準として置く。既存コードの各数値・細部を検証済みの正解として自動採用する、という意味ではない。

- 同じ有効入力・条件なら役職率と期待勝率の意味が一貫する。厳密な値と表示上の丸めを区別する。
- 役職人数など全体の整合性を保つ。各人の独立確率の積へ置き換えない。
- 本人だけの秘密を公開情報や他者の行動判断へ漏らさない。
- 設定済み戦略、合法手、実際に起こる結果のルールを混同しない。未対応のmaxを黙って均等へ変えない。
- 過去地点の条件と公開・取得の時点を保つ。訂正・撤回・戻る後に旧入力や旧結果を混ぜない。
- 入力矛盾、未対応、証拠不足、予算超過を完成した数値に見せない。再読込・キャッシュの有無で意味を変えない。

一方、既存のクラス数、関数分岐、データの重複、legacy形式、キャッシュ配置、画面用データの組立て方は維持要件とはしない。

後続の発見は「現行の確認事実」「維持すべき振る舞い」「置換できる実装手段」「仕様決定済みの将来要件」「仕様から未決」に分類する。不具合や要件との不一致は維持対象から分け、未決を新案で勝手に埋めない。

### 5. 評価軸

| 軸 | 各案を比べる質問 |
| --- | --- |
| 正しさ・情報の境界 | 計算の意味、共同配置の整合性、合法手、本人情報の境界を守れるか |
| 理解しやすさ | 1盤面の確定／入力／計算と、一つの操作による変化を短く説明できるか |
| 更新と再計算 | 誰が何を持ち、いつ継承・更新・無効化するか追えるか |
| 履歴と互換性 | 戻る・訂正・既存保存の再生を、古い結果の混入なく扱えるか |
| 将来への対応 | 追加要件をどこへ接続するか説明でき、未決部分を隔離できるか |
| 実現・検証の負担 | 重複を減らせるか。段階移行・比較検証が可能か。計算量や保持量が増えないか |

理解しやすさだけで計算の意味を変更しない。少ない項目数や単一クラスを、それ自体で高評価にしない。速度改善は測定前に約束しない。

## 既存確認事実：今回の提案と分けて保持

公開v0.5.1について、直前の読み取り調査で確認した事項。

- 保存ゲーム・履歴・Board graphと、計算用Boardは別。計算Board自体には親ポインタがない。[保存ノード](../werewolf/board_owned_log.py)、[計算Board](../werewolf/exact.py)
- 各人の役職率は全体配置候補から集計する。勝率はBoardの保存フィールドではなく評価の戻り値。[役職率](../werewolf/exact.py)、[Forecast](../werewolf/forecast_result.py)
- 画面は入力再生・役職率・勝率結果を組み合わせる。[replay / render_main](../app.py)
- 初回group配分と進行後の条件付けは別。公開／本人の条件も分離されている。[初期配分](../werewolf/exact.py)、[本人表示](../werewolf/private_adapter.py)
- 再生関数や旧・新の入力経路が併存している。存在自体を将来の維持要件とはしない。[占い経路の再生](../werewolf/seer_manual.py)、[Log投影](../werewolf/public_log_changes.py)
