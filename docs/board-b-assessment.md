# B案 c6dd475：合意済み評価軸による再評価と遅延検証

評価対象：旧 `ec513c2eb60bd20d5dbfbbe6c29bceb5648ff049` と
B `c6dd47539644c65e83c708b824b7792410c62130`。製品コード・予算・既存期待値は変更していない。

私の評価は、**Board単位で入口と責任を追いやすくした方向は支持するが、実装全体が単純に
なった、変更・拡張が容易になった、性能が良くなったとはまだ言えない**、である。
既存対応範囲の意味保存には回帰と今回の比較の証拠がある。一方、履歴再構成・根拠の確認・
再利用管理の層が新たな実装負担となり、測った7人ケースのcoldは約35〜36%遅く、
同じ入力の再評価には完了結果cacheの入口を外れた大きな退行がある。

### 一層除去という局所実験の範囲と代償

3反復・2ケース・cold/warmの12要求で全結果が通常Bと一致した。
既存の投影・評価カーネルは維持し、生成Boardの証拠再生・登録・key管理等を診断だけで外した。
**製品へ採用しない。** 根・履歴からの再構成というBの責任も外し、個々の既知例で数値が
合うことを理由にその責任を削るのは今回の設計方針に反する。

ブロック順の実験で時間的な交絡は残る。反復・CPU・背景負荷で確認したが、厳密な全要因分離ではない。
診断patchの初期化コストも除去側に含まれる。単一命令の削除ではなく、**一つの構造層**の効果である。

## 7. 次の改善案と構造上の代償

### 最優先：B境界での完成Forecast再利用

同一入力再表示の利益が最も大きい。publicに限った小さなLRU等から検証し、missでは現在の
SavedOriginと3a→3bを維持する。完成値だけを保存し、Pending／途中状態を完成cacheに入れない。
ここでは実装していないし、上記ミリ秒値をそのまま製品の改善保証にはしない。実使用のcold/warm比率は未測定で、全操作で最大の体感改善になるとはまだ証明していない。

keyはGameDataのcast・全rule、完全な有効入力と必要履歴、初期CO事前／後の観測の意味、
継続方針、視点、必要な本人情報、計算モードと予算を含める。publicと本人cacheの境界を守る。
同じ役職率だけだから、同じboard IDだから、同じaliveだからという理由で再利用しない。
key衝突・依存漏れ、bounded保持量、cache hitでも既存deadlineを守る責任が新たに生じる。

必要な検証は今回の15変更ケースを新cache自身へ適用すること、親訂正・撤回・再進行・
cache有無・初日COと後のCO・公開報告時点・死体/GJ・本人行動履歴を含む既存回帰、
旧子の復活や公開への秘密混入がないこと、LRU eviction・低予算／Pending再試行である。

### 次点：証拠層のcopy・key・prefix再生を局所化

同じ入力の完了stepを再利用する現行方針を保ち、identity用の候補copy、不要なsnapshotや
同じprefixの走査を減らす候補を個別実験する。数値再利用の前提を明示し、根からの
基準再構成を無効化できる検証経路は残す。現段階では個々の改善量は未測定。

代償はcanonical key表現、prefixの依存・失効、保持量上限、互換入力／将来秘密field追加時の
保守責任が増えること。keyだけが別の正本になったり、計算済み親重みを無条件にfilterする
経路へ戻らないようにする。GC停止や層除去をそのまま採用する提案ではない。
