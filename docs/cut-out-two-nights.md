# 6人・二夜の継承比較（独立試作）

明示的な `adapt_six_model_a` のみ6人・狼1・占い1・狩人0・霊0/1を受け付ける。既存の `adapt_model_a` は4–5人のまま。通常factory・UI・公開設定・サーバーは変更していない。7人・max・狩人へは拡張していない。

6人では初日処刑→一夜目→二日目処刑→二夜目の決着枝が発生する。既存均等行動、初期random_white、未訪問優先の占い、既存full-disclosure/偽報告均等を使用する。新しいCOや報告方針を導入しない。私有条件は本人役職と本人取得結果だけで、公共方針へ漏らさない。

## 二周目で確認した意味

既存勝率フローは終端で値だけを返し、終端Boardの秘密状態を通常は実体化しない。そのため `capture_terminal=True` と `restore_terminals` で、保存された取得前sourceから `ActionEvidence(..., terminal_payoffs=False)` を明示的に再構築する。終端で勝手に秘密を省いたまま共同分布一致と扱わない。

全個人再帰の終端状態および既存の純粋なproject処理と、公開/本人共同分布・役職率を含む全Table・行動/翌朝/決着勝率・条件付き枝mass・past・物理Boardが厳密一致。各recipeは同じSavedOriginを保持する。計測中の `prepare_evaluation` 呼出しを禁止して、子で初期priorを作り直さないことも検証した。

二夜目の取得rosterは三つ。処刑された所有者は次の取得を持たず、夜に死亡した所有者は死亡前の取得を秘密履歴として保持する。元の全プレイヤーが対象領域で、未訪問が残る間は再訪問を禁止し、死者も合法対象に含む。両夜のWolfAttackを保持し、終端後の朝報告は作らない。二日目の朝の生存者のみが取得結果を公開する。霊COを含む既存報告フローも同じ対照を通した。

群は初期証明から公開の死亡/報告端点、本人既知情報、狼本人rosterで細分する。二周目の全評価sourceについて、群内の既知transpositionがBoard・公開/本人完全法則を保つことをテスト側だけで監査。実行時に置換探索・交換照合へ戻らない。

## 有限計測

再現: `python -B -m benchmarks.player_match_groups.cut_out_two_nights_fixture`。公開例を新規プロセス3反復、本人占い・本人狼・霊COを各1回。全体 18.641 秒。各プロセス60秒、全体300秒、Windows WorkingSet/peak監視1,500,000,000 bytesで停止する。評価entry内部はさらに25秒制限。全suite・重いworkerは実行しない。

|---|---:|---:|---:|---:|

| public #2 | 0.236 / 1.041 | 2.329 | 3.371 | 63.2 |
| public #3 | 0.234 / 1.046 | 2.331 | 3.376 | 63.3 |

| own-wolf | 0.081 / 0.302 | 0.618 | 1.195 | 40.2 |
| medium | 0.479 / 0.986 | 2.095 | 3.695 | 69.6 |

全例の村勝率は3/8。公開3反復の評価中央値は切り出し 0.235秒、全個人 1.046秒。条件内の有限計測であり、一般人数・秘密状態増加時の性能は保証しない。

JSONはimport/startup、正式初期adapter、SavedOrigin一致gate、群維持 `cut_out_seconds`、試作scalar/actionキー維持 `key_seconds`、法則取得/朝生成/子再構築 `law_seconds`、残りの評価、ラベル値復元を分けて記録する。共通recipe内部のsource-key費用は子再構築側に含まれ、試作key_secondsだけで全cache費用を表すものではない。再帰包含のinclusive_action_secondsは加算不可。

**全ラベルの終端木を代表枝から効率よく復元する処理は未実装。** 今回は明示的な全個人走査で全ラベル履歴を実体化し、その評価＋終端recipe読戻しを `full_label_materialization_seconds` として計上した。旧全置換探索ではないが、追加の全個人走査を要する。切り出し評価＋この全ラベルpass＋起動/初期準備の合計もJSONに記録し、別にプロセス全体の検証完了時間を示す。全終端木が必要な用途まで高速化できたとは主張しない。

ピークは両engine・全終端recipe・検証を含むプロセス全体。engine別メモリ削減の証拠ではない。公開例の切り出し側は終端286件（二夜目227件）、全個人側は1572件を再構築した。本人狼は85/393件、霊COは750/1570件。枝数は同じ役職配役を含む観測/本人条件別recipe数で、配役数ではない。

## 残件と拒否範囲

6人SavedCutOutGraphの初期生成から決着までの比較は対応したが、旧第一朝専用 `SavedBinding.bind/corrected` の6人訂正registryは未対応。一般の途中Board編集・取消UI、任意のCO変更・再CO方針、占い2人、7人、max、狩人、三夜目以降は対象外。正式kernelのPendingを均等化や情報省略で補完しない。

最小二夜ケースで既存仕様の未対応による停止は発生しなかった。通常/公開接続なし。証拠: `cut-out-two-nights-results.json`、2本の新規回帰＋既存11本（計13本）の成功ログ `.artifacts/test-cut-out-two-nights-final.log`。
