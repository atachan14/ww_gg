# 切り出し型一致グループ方式：独立試作の最初の区切り

内部名は `PartitionedMatchGroups`、旧方式は「照合型」。通常factory・PlayerData本体・既存評価器は変更していない。公開・既定有効化・旧実装削除は行わない。

## この段階で実装したもの

4〜5人、狼1・占1・狩0・霊0/1、全潜伏の対称な初期共同分布を既存の配役列挙と均等占い生成から構築する。初日占いはなし／通常／ランダム白。入力された任意分布が対称だと推測する入口は設けない。設定済み方針は均等のみを受け付け、max等は `UnsupportedPartition(reason)`。均等への黙った置換はしない。

初期の対称性はS_n。以後はCO、報告元・対象、記録された生死、選択したactor/target、単独本人の役職・取得結果に対して、保証できる交換関係だけを残す。公開CO・初日報告はDay1昼の小fixtureに限定。これは**完全な共同分布への支持条件付け**であり、Model Aの公開配役重みの更新、虚偽報告の生成確率、夜の物理遷移、勝率計算の新実装ではない。生死と選択は外から与えた位置・関係の記録で、襲撃／処刑の尤度や行動方針を生成しない。

各 `PlayerComparisonInfo` は一つの不変 `SharedContext` を参照する。contextは基準分布・設定・公開/本人の完全共同分布・CO・生存者・順序付き履歴・保証済みグループ・基準分布上の支持質量を保持する。プレイヤーごとの共同分布の重複コピーはない。現在のPlayerDataへの接続はまだ行わず、その比較情報に相当する独立した読み取り専用コンパニオンを用意した。

同じcontext内での比較は `(contextの同一性, block番号)` だけ。別の再構築・履歴・設定・本人視点のcontext同士を共通キーで比較する機能は未実装で、安全側に不一致とする。公開用の行へ本人contextを公開する接続もない。

## 保証と処理の所在

初期生成が完全な配役・取得履歴の共同分布について交換不変であることを構築規則から保証する。更新時は、以前の各ブロック内のleader交換が**順序付き観測プログラム全体**を保存するかを確認する。各対応済み条件付けは番号交換と可換なので、そのプログラムを保存する交換は、条件付け後の公開・本人の完全共同分布も保存する。leader交換が生成する各ブロック内の全置換だけを保証する。

色・次数・WL一致だけではまとめない。例えば同じ入出次数の4位置の巡回選択関係では、回転対称性はあっても任意の二位置交換は成り立たないため、試作は単独群まで切り出す。最大の対称群を発見するアルゴリズムではない。共有不足は許容し、過剰な共有はしない。

| タイミング | 現在行う処理 |
|---|---|
| 初期構築 | 小さな全配役・取得履歴を明示生成。対称性の全置換探索はしない |
| CO/報告/本人条件更新 | 共同分布の支持フィルタ・正規化。元の支持質量も保持 |
| グループ更新 | 継承した候補ブロック内の生成元交換と履歴の比較。全n!探索や共同分布の置換照合をしない |
| 行構築 | 完全共同分布から正確な役職率を計算し、context参照と群番号を渡す |
| 行同士の照合 | context参照と群番号だけ。履歴走査・正規化・置換探索なし |
| 未対応 | 理由付きUnsupported。旧照合型への隠れたfallbackはない |
| 検証oracleのみ | 旧配役/秘密状態の完全列挙、既存state_signatureでn!検査、旧完全canonical_keyとの対照 |

更新時には現状、各既存ブロックについて履歴全体を確認する。変更依存グラフを使い、必要箇所だけを更新する最適化はまだない。`generator_checks`、`joint_normalizations`、`support_mass_scans`、`role_rate_builds`、`comparisons` を分離して記録する。試作の `full_permutation_searches` は0。初期列挙・条件付け自体が無くなったという意味ではない。

## 小fixture

市2霊1占1狼1、ランダム白では、初期60配役180秘密状態を保持する。

- 全潜伏：`{1,2,3,4,5}`。
- P1/P2の同時CO：`{1,2} / {3,4,5}`。
- 同じバッチで両者がP3白：`{1,2} / {3} / {4,5}`。秘密状態は6件。霊がP3の群の質量1/3、P3が市の群の質量2/3を保持する。
- 同じ生存者全員から一様に位置を選ぶ例は、群質量2/5・1/5・2/5と元の位置数2・1・2。これは実行可能なゲーム方針を新たに生成したものではない。
- P4がP1を選択した記録を加えると、P1/P2にも関係変更が波及して分かれる。
- P1本人の役職・取得結果を条件付けると公開法則は保持したまま本人法則を区別する。取得後の本人死亡（Day1夜の記録）を加えても取得結果は残る。

基準からP1真占だけを本人条件とした別fixtureでは12配役36秘密状態、白対象各1/4。P3白を本人条件に加えると対象の霊1/3・市2/3を保持し、他人の秘密を独立化しない。

`RoleCell` はグループごとの役職人数の**共同**組成、元の配役数、秘密状態数、正確な質量を示す補助要約。秘密履歴間の相関の代用キーではなく、完全法則はcontext内に残す。初期から秘密法則そのものを圧縮して勝率探索する実装はまだない。

## 取消・訂正・時系列

更新は既存群を壊す方向のみで再結合しない。CO取消、報告訂正、本人視点の取り替えは `rebuild(active_program)` により同じ基準から作り直し、消した条件に応じた共有を取り戻す。

一つの `Observation` の行は、明示された同時バッチのunordered multiset。別バッチは順序を保持する。例えばfilled条件でP1だけがCOした時点の条件付けを観測してからP2がCOした履歴は、初めからP1/P2が同時COした履歴とは異なる。現在COだけに潰さない。訂正時に同時バッチへ変更するか、元の順序を残すかは呼び出し側が明示する。現行アプリ履歴の自動変換は未実装。

## 検証と残件

再現：`python -B -m benchmarks.player_match_groups.partitioned_fixture`。新規9テスト、12初期条件、42通りのCO/白報告位置fixtureを、既存の明示列挙と比較する。役職率・完全共同分布・支持質量・群内全置換の妥当性・multiplicityを検査する。単独巡回グラフ、履歴順、訂正/取消、本人/死亡、未対応条件も含む。証拠は `partitioned-fixture-results.json` とローカル `.artifacts/partitioned-fixture-tests.log`。

200回の行照合では比較counterだけが200増え、生成元検証・正規化counterは増えない。これは処理の所在の確認であり、旧方式より速いという測定ではない。新規テストは過去の878件全suiteとは別の検証で、合算して全suite完了とはしない。

全ゲーム勝率、Model Aを含む共通評価フローへの接続、通常PlayerDataへの組込み、文脈を跨ぐ比較キー、生成方針に従う公開報告/複数夜/GJ、hunter/max、7/9人、初期法則そのものの圧縮はこの区切りの対象外。新しい方式の性能比較も未実施。旧照合型と通常経路を残した独立試作としてのみ完成している。
