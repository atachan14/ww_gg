# 全体レビュー(2026-10-30)

v0.6 の区切り方と、今後の作り方(作り直す・リファクタする・このまま最適化する)を決めるためのレビュー。基準はローカルの `7cb8506`。コードは変えていない。

## 結論

- **「このまま最適化する」は勧めない。** 重さの原因が一か所に集中していない。しかも、同じ計算を別の経路で行う評価器が何本も並んでいて、どこを速くしても効果がその経路に限られる。
- **勧めるのは、「計算の芯だけを新しく作り、今のコードを答え合わせに使う」案。** 画面(UI)と HTTP の形はできるだけ残す。今の `werewolf/` は消さずに、新しい芯の数値を照合する相手にする。新しい芯が同じ範囲の数値を出せるようになったら、画面の接続を切り替えて、古い芯を archive に移す。3つの案の、1(作り直し)と2(リファクタ)の中間にあたる。
- **その前に、計算の定義を文書に固定する。** 今の複雑さの一部は、実装ではなく要件(計算の定義)から来ている。どこまでを v1 の範囲にするかで、新しい芯の大きさが大きく変わる。決めてほしいことは「決めてほしいこと」の節にまとめた。
- **v0.6 は公開せず、Preview の状態で凍結する案を勧める。** 公開の前に残っている作業(Vercel での保存、プロセスをまたぐ計算、時間切れからの再試行)は、新しい芯では作りが変わる部分なので、今仕上げても無駄になりやすい。

## 残したいもの(ユーザーの希望)と、それぞれの扱い

| 残したいもの | 扱い |

## 分かったこと

### 1. 計算の定義そのものに、避けにくい複雑さがある

今の計算は、情報が隠れたゲーム(不完全情報ゲーム)で、次のように定義されている。

- 役職の割り当ては1つに決めず、公開情報と矛盾しない「世界」をすべて重み付きで持つ。
- 昼の処刑は、村が全員で共有する**公開の信念**(Model A)を使って、村の勝率が最大の候補を選ぶ。
- 夜の襲撃は、狼が知っていること(仲間、自分の襲撃の履歴、GJ から分かった「その人は狩人ではない」など)を単位にして、狼の勝率が最大の候補を選ぶ。真の配役を見てから選ぶことはしない。
- 占い先と護衛先は均等に選ぶ。偽の報告は max か random。
- 勝率は、こうして決めた方針の下での、実際の分岐の確率(**物理的な分布**)で集計する。

ここで、公開の信念(Model A)は「矛盾しない世界を残す」だけで、「狼がその人を噛んだのだから、その人は〜だろう」という選択の確率による推理はしない(2026-10-13 にユーザーが A 案を選んだ。旧記録は `archive/20261029/wolf-information-set-investigation.md`)。そのため、**判断に使う分布と、勝率を集計する分布が別のもの**になる。これに、本人だけが知っている情報(占い結果、護衛先)と、本人の視点で見た表(私的な視点)が加わる。旧 docs では、少なくとも次の4種類の分布・記録を区別している(`archive/20261029/expected-win-policy-common-design.md`)。

| 記号 | 中身 |
|---|---|
| L | 完全な秘密の履歴(配役、占い・護衛・襲撃の記録) |
| Q | 公開の信念(Model A の重み) |
| B_i | 本人の信念(Q を本人の知っていることで条件付けたもの) |
| P | 実際の分岐の確率 |

この定義の下では、状態に「誰が何を知っているか」を持たせる必要がある。役職の数を数えるだけの単純な状態にはできない。**この部分の複雑さは要件から来ていて、作り直しても消えない。** ただし、1つの芯の中で一貫して表すことはできるはず。

もう1つ、途中の盤面を手で編集して、そこから計算を始め直す機能がある。この場合、過去の他人の秘密(狼が過去に知ったことなど)が盤面だけからは決まらない。今のコードでも、ここが繰り返し問題になっている(`archive/20261029/current-model-structure-review.md` の5節)。

### 2. 実装は、後から足した経路が重なって散らかっている

| 見たこと | 数字 |
|---|---|
| 計算のコード `werewolf/` | 124ファイル、約1.8万行。app.py から import でたどると、123本中118本がつながっている |
| 7人のケースの計算で、実際に関数が呼ばれたモジュール | 58本 |
| 評価器の系統 | `InformationSetForecast`(名前付きの基本)、その子の `GroupedForecast`(グループ化)、`RootSecretEngine`(狩人あり)、`anonymous_value.Evaluator`(人数で数える。全員潜伏・霊能なし・狩人なしだけ)、`EvaluationGraph`、証明書の系統(`wolf_profile_certificate`、`policy_certificates`、`win_certificate`)、`fixed_actor_continuation`、`match_groups`(既定は無効)、どこからも使われていない `seer_future_forecast`・`wolf_view_forecast` |
| 「この組み合わせは未対応」として止める箇所(`Pending(...)`) | 123か所。同じ配役でも、入口(MAIN か Tree か)によって計算できたりできなかったりする。例: Tree の計算(`ClosedCalculation`)は、狩人がいると、昼・夜・偽の報告がすべて random のときだけ動く |
| 機能の切り替えフラグ(`*_PREVIEW` など) | 約10個。Production・Preview・ローカルで有効なものが違い、組み合わせごとに経路が変わる |
| 評価器の外から属性を書き込んで、動作を変えている箇所(`engine.xxx=...`) | 21か所 |
| 中心の再帰 `InformationSetForecast.solve` | 約80行の中に、キャッシュのキーの作り方が4通り(`value_law`、`full_renamed_key`、`renamed_value_key`、`private_value_key`)、近道が3つ(勝ち確定の証明、人数だけで決まる場合、昼の勝率1)、記録用の呼び出し(`evaluation_graph`)、台帳(`acquisition_provenance`)が入っている |
| テスト | 338ファイル、約2.8万行(計算のコードより多い)。うち移行の確認用の `test_cut_out_*` が39ファイル・117テスト |
| `benchmarks/` | 640ファイル |
| コードの書き方 | 1行に複数の文を詰めた書き方が多く、読むのに時間がかかる |

`AGENTS.md` の方針(「定義した式を計算する最小のアルゴリズム」「製品のループに台帳や証明を入れない」「ケース専用の評価器を足さない」)と、今のコードには大きな差がある。方針は正しいけれど、継ぎ足しの開発の中で守りきれなかった、というのが実態だと思う。

### 3. 重さの原因は、1状態あたりの処理が重いこと

PERFORMANCE.md の7人のケースを、関数ごとの呼び出しを記録しながら計り直した。記録のせいで遅くなり、全体は175.6秒だった(記録なしでは約75秒の記録がある)。結果は 89/224 で、記録どおり。

- 評価した状態は約3.1万個、行動の値は約5.7万件、`solve` の呼び出しは40,692回。**問題の大きさとしては、それほど大きくない。**
- 時間は特定の場所に集中していない。上位は、組み込み関数(ハッシュ2千万回、`any`・`getattr`・`isinstance` など、計27%)、分数の計算(11%)、状態オブジェクトの生成と検証(`TrueScanState`・`Hypothesis` の `__post_init__`、`normalize`、`dataclasses.replace`)、グループ分け(`group_partition`)。
- 関数の中に書いた import が、計算の途中で約400万回実行されている(約2%)。
- 記録なしの約75秒を3.1万状態で割ると、**1状態あたり約2.4ミリ秒**。

9人にすると状態の数は大きく増えるので、1状態あたりの処理を軽くするだけでは足りない可能性が高い。人数の伸びに効くのは、**同じ立場の人(同じCO、同じ公開結果)を名前で区別せずに人数で数える表し方**。今のコードにもこの考え方(`anonymous_*`、`group_partition`、`exact_renaming`)はあるけれど、後から別の経路として足されているので、使える範囲が狭く(全員潜伏・霊能なし・狩人なし、など)、変換のコストもかかっている。

新しい芯では、最初からこの表し方を土台にして、1状態あたりの処理も軽くする(分数の扱い方、生成時の検証を外部入力の境界だけにする、キーを小さくする)。どれくらい速くなるかは、まだ見積もりにすぎない。小さい試作で確かめる。

## 3つの案の比較

| 案 | よい点 | 問題 |
|---|---|---|
| 1. 全部 archive して0から作り直す | 構造を一から決められる | UI・HTTP・保存の形まで作り直すと、無駄が大きい。数値の答え合わせの相手を失いやすい |
| 2. 設計だけやり直して、今のコードからリファクタする | 動いている状態を保てる | 経路と分岐の条件が多すぎて、1つずつ移すと時間がかかる。移行の途中の互換の層がまた増える(今の `cut_out_*` がその例) |
| 3. このまま最適化する | すぐ始められる | 重さが一か所に集中していないので、効果が小さい。評価器が分かれているので、9人まで伸ばせる見込みも立たない(2026-10-17 の判断と同じ) |
| **勧める案: 計算の芯だけ新しく作り、今のコードで答え合わせする** | UI・方針・数値を残しながら、芯は定義から作れる。今のコードを「正解の候補」として使える | 新しい芯が今と同じ範囲まで追いつくまで、2つの芯が並ぶ。範囲を絞って段階的に広げる必要がある |

## 勧める進め方

1. **計算の定義を文書にする**(`docs/spec/` に新しい文書)。状態、各行動の選び方、分布の種類と、それぞれの使い道、終了の判定、途中の盤面から始める場合の扱い。数式で書けるところは数式で書く。次の節の「決めてほしいこと」の答えもここに入れる。
2. **v1 の範囲を決める**(配役、戦略、視点、Tree、編集)。
3. **新しい芯の小さい試作を作る。** 例: 市民・霊能・占い・人狼で、全員 max。PERFORMANCE.md の7人のケースで、89/224 と同じ値が出るか、時間がどれくらいかを確かめる。ここで、作り直しの効果があるかどうかを判断する。
4. 効果があれば、範囲を広げる(狩人、私的な視点、Tree)。各段階で、今のコードと独立した列挙の両方と照合する。
5. 画面の接続を新しい芯に切り替える。古い芯と、それ専用のテストを archive に移す。

## 決めてほしいこと(ユーザーへの質問)

1. **公開の信念は Model A のままでよいか。** 村は「矛盾しない世界を残す」だけで、狼の選択の確率からは推理しない。B 案(選択の確率も推理に使う)は数値が変わり、計算もより難しくなる。A のままなら、新しい芯も A で作る。
2. **私的な視点の表(占い師・狼・狩人の視点で見た確率と勝率)は、v1 に必要か。** 必要なら、本人の信念 B_i を最初から芯に入れる。
3. **途中の盤面を手で編集して、そこから計算を始め直す機能は、どこまで必要か。** 例: (a) 初日の昼だけ自由に編集できる、(b) 過去に戻って編集し、そこから作り直す(今の Tree)、(c) 任意の盤面を、独立した出発点として計算する。(c) は過去の秘密の扱いを新しく決める必要がある。
4. **v1 の配役と戦略の範囲。** 役職(市民・霊能・占い・狩人・人狼、狩人は1人まで?)、戦略(昼・夜・偽の報告の max/random、結果の公開の設定、CO の条件)。全部の組み合わせを最初から対応させるか、よく使うものから始めるか。
5. **GameTree と履歴の保存は v1 に必要か。** 必要なら、保存の場所(ブラウザ内だけでよいか)。
