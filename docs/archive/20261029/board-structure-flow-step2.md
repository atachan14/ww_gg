## まず分かったこと

**確定／入力／計算という3区分と、分岐確率×子の勝率による加重集約の大枠は、元案ですでに表現されている。今回の確認対象は、現行・将来の意味をその中でどう具体化する必要があるかである。**

分類名そのものに表現不能な問題があると確認したわけではない。元案が役職候補・履歴を持たない、全未来枝を保存する、単一の率だけを持つと決まったわけでもない。入力の所属と時点、全員分の配置と必要履歴、誰が何を知るか、どの行動を固定したか、結果の有効条件は、元案で未記述のため確認・具体化する事項として扱う。どこへどう配置するかはStep3の比較事項であり、本書は新設計を選ばない。

```text
保存された進行＋その地点に属する入力
                    ↓ 再生
現在の公開条件＋全員分の候補＋必要な秘密履歴
          ├─ 各人について集計 → 役職率
          └─ 誰の情報で行動を選ぶか
                         ↓
                 行動と結果の分岐
                   ├─ 終局 → 利得
                   └─ 継続 → 次の判断へ
                         ↓ 確率で加重
                  各種類の勝率・未計算理由

入力訂正／視点変更／戦略変更 → 何が変わったかに応じて再構成・再計算
```

これは必要な意味の接続図。既存の関数・保存形式・公開と物理の保持オブジェクトをそのまま残す要件ではない。

## 2. 一覧：何がsimple表現に足りないか

以下は元案の不足を断定する表ではなく、未記述点を具体化するための確認表。「役職率だけ」「単純な上書き」等は元案の決定事項ではなく、そのように省略した場合のリスクである。「追加情報で表現可」は意味上の判定であり、元案にその情報を追加できないと判断したものでも、新フィールド・保存方式を設計したものでもない。

| 論点 | 現行の事実 | そのように省略した場合のリスク（元案の断定ではない） | 表現に必要な情報・区別 | 判定 |
| --- | --- | --- | --- | --- |
| 保存盤面と未来枝 | 保存ノードは選んだ進行・所属入力。未来評価は結果枝を一時生成する | 全未来枝を必ず保存する／画面の子だけで勝率を求める、と誤解する | 保存された選択経路と、計算で検討した候補・結果 | 区別を加えれば可 |
| 親からの保持 | 過去設定・公開制約・報告を再生し、必要な取得／護衛／襲撃を残す | 直前の役職率だけを受け継ぐと、相関や合法手を失う | 共同候補、当時の設定、必要履歴と入力所属 | 共同候補・履歴の保持範囲を確認 |
| 初期COgroup | 初日スナップショットだけ重みを定義し、以後は条件付け | 各子で等配分をやり直すと別の推論になる | 初期配分の基準と、後続の観測・条件付け | 同じ「正規化」で一括しない |
| 公開／本人 | 同じ公開地点でも本人の既知役職・結果・行動で条件が違う | 表示を切り替えると公開入力まで変わる／他人の秘密で選ぶ | 観測者と、その主体が知る情報 | 条件を区別すれば可 |
| 選択時の想定／結果の質量 | Model Aの公開配役重みと、物理枝の重みは異なる場合がある | 役職率をそのまま全分岐確率に使うと値が変わる | 行動判断に使う想定と、起きる結果の確率 | 判断と結果で使う確率の意味を確認 |
| 勝率の意味 | 現在、固定行動、朝まで、累積は別 | 村勝ち＋狼勝ちをどの欄でも1にするなどの誤り | 評価対象・期限・条件・確定済み質量 | 種類を区別すれば可 |
| 行動・観測・未入力 | 固定行動、実際の死体、未観測と無死亡は異なる | 未入力をGJと扱う／死体を任意の襲撃介入に置換する | 入力種別と、その時点の観測済み／未入力 | 区別を加えれば可 |
| 訂正・撤回・戻る | 親の入力訂正は旧子孫を退役。子の発言撤回は親Logを消さない | 一つの削除操作で過去の事実まで消す／古い子を再利用する | 操作の意味・所属時点・後続結果の有効性 | 訂正・撤回の更新範囲を確認 |
| 未計算 | 入力エラー、証拠不足、範囲外、予算超過などがある | null/0にまとめると、0%と計算不能を混同する | 数値の有無と理由、確定入力の保持 | 明示すれば可 |
| cache | 公開入力と本人条件を区別し、完成値だけを再利用 | 入力変更前の結果・別人の条件が残る | 計算元の条件と再利用可否 | cache方式自体は置換可 |

根拠：保存は `board_owned_log.new_node / prepare / commit_owned_change`、公開再生は `app.replay / seer_manual._replay`、初期重みは `exact.group_initial_board`、率は `exact.role_probability`、評価は `model_a_public._evaluate_public_game / action_flow.action_flow`、本人は `private_adapter.evaluate_private_table`。各ファイルは末尾の索引から参照できる。

## 4. 数値が出ない理由を分ける

| 状態 | 小さい例／意味 | 現行の扱い | simple表現で落とせない点 |
| --- | --- | --- | --- |
| 合法・未選択 | 生存対象があるが進行先を指定していない | 候補比較はできるが、必要な進行操作では対象指定を要求 | 候補の存在と、選択済みを別にする |
| 未観測 | 夜明けの死体をまだ記録していない | 夜明けの進行は入力待ち | 未入力と無死亡は異なる |
| 不完全な入力 | 占い対象か色の一方のみ | 操作経路によりPending／入力拒否。新Table公開は完成行を要求 | 画面上の下書きと確定入力を区別 |
| 矛盾・非合法 | 自護衛、死亡対象の指定、真霊結果と既知事実の衝突 | 入力・ルールのエラー。公開保存を都合よく書き換えない | 0%という完成値にしない |
| 秘密履歴の支持なし | 公開配役は残るが、未訪問優先と矛盾する取得履歴など | 対応経路は支持ゼロPendingを返す | 不足を一律の秘密履歴で補完しない |
| 未対応 | 複数狩人、未設定の共同偽報告則など | 理由付きPending | 不正な入力だったとは限らない |
| 証明／予算未完了 | max方針の整合証明・探索が終わらない | Pending | 解なし・複数解・0%の証明ではない |

根拠：`app.parse_target / table_proposal / dawn_report`、`dawn.unsupported_reason`、`seer_manual.pending`、`root_secret_flow.observe_root_public`、`policy_certificates.ProfileSearch`。今回 `test_policy_certificates` の状態区別・非一様均衡を勝手に追加しない回帰2件も成功。

### 8.3 分岐率・過去の確率・勝率の意味

| 数値 | 意味 | 要件上の注意 |
| --- | --- | --- |
| 行動の選択率 | 親の条件で、設定済み方針がどの行動を選ぶか | 手動で一つ固定する比較と、方針の確率選択を区別する |
| 行動後の結果率 | その行動を固定した下で、終局・生存・報告等の結果が出る確率 | 行動選択率そのものではない。行動＋結果をまとめて見せるなら、掛けた値なのか明示する |
| 到達率 | ある基準点から複数段階を経てその枝へ至る質量 | 直前の親だけを分母にした率と区別。どの基準点からの率かが必要 |
| Current条件付きの過去内訳率 | Currentまでの情報の下で、その過去候補・履歴がどの程度残るか | 当時の前向き分岐率の逆数ではない。Current入力が変われば変わり得る |
| Board勝率 | そのBoardの条件と継続方針で、最終的に勝つ期待値 | 起点・情報条件・視点・方針・評価期限が必要。正規Boardは当時情報、過去BoardはCurrent情報で再評価。細部の計算条件は別途未決 |

各条件付きの率は、同じ分母で漏れなく重複なく分けた候補集合に対して扱う。別の行動をそれぞれ固定した比較枝や、正史・過去内訳・未来を並べた収納item全体が、合計1になるとは限らない。収納itemに固有のBoard勝率・遷移率があるかも、計算上の意味を決めずに付けない。

**最小の意味確認例（既存ケースAの分数を利用）**：市民4・狼1、初日P5処刑を固定すると、村勝ち終局1/5、継続4/5。Currentをその後の継続中の夜とするなら、当時P5狼の候補はCurrent条件の下では0、P1狼は当時1/5からCurrent条件では1/4になる。これは「過去の配置候補を見直す率」の例であり、当時の分岐率1/5を書き換える要求ではない。表示基準はユーザー回答により、正規Boardは当時情報、過去BoardはCurrent情報での再評価と確定した。この確率例だけで再評価の計算式が決まるわけではない。

元案の「分岐確率×次Board勝率を合計」は加重集約の大枠を表している。この案で追加確認するのは、同じ画面に置く率・勝率の分母と評価条件。過去内訳と前向き結果枝を同じ種類の子として無条件に足し合わせない。

**現行Model Aとの接続注意**：公開の配役重みと、実際の行動・観測に基づく物理的な履歴質量は異なる場合がある。したがって新しい「Currentからの過去確率」を、現行公開Tableの率から唯一の完全ベイズ事後として自動的に得られるとは扱わない。公開認識の内訳か、設定済み生成則に基づく履歴内訳か、どの条件・方針を使うかを要件として確認する。既存コードの保持方法を新構造へ固定する話ではない。

### 8.4 過去Boardの勝率と情報視点：表示基準は確定

> 正規Boardでは「当時の情報での勝率」を出す！過去Boardには「Currentの情報で見直した勝率」を出す！

これにより、**正規Boardは当時情報での勝率、過去BoardはCurrent情報で再評価した勝率を表示する**ことを確定要件として扱う。表示基準自体を再度未決に戻さない。

ただし、Current情報による再評価の計算式、当時の行動方針を保って候補・履歴の内訳だけを絞るのか、後知恵で過去の行動方針にも作用させるのか等は別途未決。当時その情報を知らない行動者へCurrentの秘密を黙って渡す仕様は採用していない。

反実仮想はこの表示基準とは別の対象であり、どの行動・設定を変えて評価するかは未決。公開視点／本人視点も率と勝率の両方に関わる。Current本人の知識と過去時点で本人が知っていたことを区別し、どの視点・時点の条件の値かが見分けられることを確認する。表示切替で正史の公開入力を書き換えない。

更新履歴についての追加回答：

> 更新履歴は不要な可能性が高い気がしてきてる！っていうか、そのつもりで図案からは削除しちゃってた！

図案から意図して除外した、不要寄りの案として記録する。同Phaseの更新前後をツリーへ必須追加しない。**内部の完全履歴保存を削除する承認、既存のundo・戻る・訂正機能を削除する承認とは解釈しない。**

### 8.5 既存でできることと、新しい要求

| 項目 | 現行確認事実 | この案との差分 |
| --- | --- | --- |
| 選んだ履歴の親子・現在位置 | 保存グラフにroot/current/parent/children・edge・所属Logがある | これを正史のアコーディオンとして表示する機能は新規 |
| 別進行の枝・過去入力訂正 | 別の行動による兄弟枝、戻ると再訪、訂正時の子孫退役・アーカイブがある | 同じ進行地点の情報更新前後を毎回別兄弟として見せることとは別。ユーザーは更新履歴を図から除外し、不要寄りとしている |
| 現在Boardの勝率・固定行動値 | 評価入口が盤面値・候補値・朝までの値を返す | 全保存ノード・全未来ノードへ常時保存・表示する構造ではない |
| 未来の結果枝とその確率 | 計算カーネルに確率付き結果枝があり、加重評価する | 全未来木を描画・永続化する機能ではなく、状態共有・簡約・打切りもある |
| 過去の再生 | 保存入力と当時設定から再構成する | Currentを条件とした全祖先の内訳一覧・勝率一覧を返す一般機能はない |
| 秘密履歴の再構成・条件付け | 対応経路では取得・護衛・襲撃の共同履歴と公開／物理の条件付けがある | それだけで任意の過去内訳や反実仮想を表示できるとまでは確認していない |
| 分岐要因 | edgeに対象・方針・死体観測などの記録がある。計算枝には結果がある | 「処刑Player」「襲撃意図」「公開死体」「能力結果」等の見せる意味を整える必要。秘密襲撃を公開原因として表示しない |

根拠：`board_owned_log.path / new_node / prepare / commit_owned_change`、`exact.BoardOutcome / action_outcomes / Progress`、`model_a_public.public_forecast`、`root_secret_flow.observe_root_public / replay_root_secrets`。前回確認済みの親子・訂正・本人情報分離の回帰も参照する。今回、過去の一般的な平滑化・反実仮想APIを実装・実行検証したわけではない。

### 8.6 計算・保存・描画のコストを別々に考える

| コスト | 増える条件 | 今回固定しないこと／確認事項 |
| --- | --- | --- |
| 計算 | 各過去地点の再評価、各視点・Current条件、全行動・能力・報告の未来枝、方針整合証明 | 折りたたみだけで計算が軽くなるとは言わない。展開時に求めるか事前に求めるか、どこまで完成させるかは後の検討 |
| 保存 | 全未来枝、完全な秘密履歴、各入力更新前後の同Phase版、結果の複数条件・revision | 現行の保存は署名cookieを使い、app設定のcookieサイズ警告基準は4093 bytes。全木をそのまま保存して足りると仮定しない。別保存方式の採用も今回は決めない |
| 描画 | ノード数・長いラベル・アコーディオンの入れ子・スマートフォン幅 | 折りたたんでも全DOMを先に作れば負担は残る。表示件数・操作の改善は後の試作で確認 |
| 更新・cache | Current入力・視点・方針が変わるたびに過去再評価と未来結果の条件が変わる | 当時値とCurrent再評価値を同じ結果として再利用しない。どの条件・版の値かを追う必要。新しいcache方式は未選定 |

未来木は複数候補の積で増え得る。同Phaseの更新前後を保存する場合も、編集回数・分岐数に応じて版が増える。現在の状態共有や簡約は計算結果を保つための実装手段であり、全枝描画用の独立ノードが既に用意されているという意味ではない。

今回は追加の性能測定・UI試作をしていない。遅延生成、表示上限、永続化範囲などを採用したと読める具体設計は置かない。画面を折りたたむこと、描画を省くこと、数学的評価を打ち切ることは別であり、表示都合で厳密な勝率を別の値へ変えない。
