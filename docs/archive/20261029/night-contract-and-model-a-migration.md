# 夜の共通契約と全体側のモデルA移行準備

2026-10-13、基準128feaf。今回は仕様不変のローカル整理のみ。新役職、BoardOverview切替、新旧モデル選択UI、push/deployは行わない。旧公開計算は恒久的な比較オプションではなく段階移行の残りとして扱う。

## 今回実装した契約

action_flow.NightFrameは、選択済み対象、死亡前Board、取得前payload、取得後payloadを渡す。night_outcomesが取得後に死亡枝を返す。現行の占いはunchanged_death_outcomesを使い、取得が死亡を変えないという契約を明示する。共通flowが終局停止、死亡後の射影、朝報告、次評価を処理する。

旧公開はterminal_preflight_safe=Trueとして、死亡結果に影響しない現行取得だけなら終局枝の取得生成を省略する。AはFalseとして従来どおり先に取得と閲覧者条件を検証する。死亡を変える能力のresolverはFalseにし、取得前の終局判定を使わない。専用の記録用policyで、選択済み対象が変わらず取得後payloadがresolverへ届くことを検証する。狩人やGJのゲーム値は生成しない。

night_acquisition.acquire_lawsは、同じ死亡前名簿で公開と私的取得分布を別々に生成する。生成callbackへ閲覧者条件を渡さず、observerは私的側だけを絞る。旧公開評価、A、参照用旧wolf solverが共有し、生成/cache/予算の契約は各callbackが保持する。

information_weights.observer_report_weightsは公開報告の尤度を私的枝の重みへ移す同じ処理をAと参照solverで共有する。公開枝の重みを変更せず、私的枝の合計1を検証し、不完全な枝を再正規化して正常値に見せない。

| 段階 | 入力/出力 | 情報の所有者 |
|---|---|---|
| 対象候補/選択 | day_scores、wolf_policy→対象/選択確率 | 昼は公開、狼は公開＋初期仲間。閲覧者の条件は使わない |
| 夜の取得 | acquire_laws→AcquiredLaws(public,private) | 公開判断用の共同priorと閲覧者条件付きpriorを分離 |
| 死亡生成 | NightFrame→FlowOutcome | 現行は元の物理分布と既存action_outcomes。公開更新は各policy |
| 公開観測更新 | phase_updates、各ActionPolicy | Aは死体整合性だけ。指定行動の旧条件付けとは別 |
| 朝の報告/次評価 | report_flow、observer_report_weights、continuation_value | 報告生成は公開入力、重みは公開/私的で分離 |

護衛なら夜の能力決定/防御状態をNightFrame.afterへ持たせ、night_outcomesへ差し込む位置ができた。同じaction_flow/report_flowを使えるが、死体なし/複数死体のBoard遷移、観測の識別、情報所有者と相関、終局位置、役職状態は未定義。別solverを新設する必要はないという設計上の入口であり、護衛の実装完了ではない。

## 削除と高速経路

wolf_view_forecastは本番APIから未使用でも参照テストがあるため、まだ死んだ処理と断定して削除しない。seer_future_forecastはBoardOverviewから現役。どちらも公開切替・呼出し検索・回帰の移管後に評価ループを削除できる候補。exact.Board/action_outcomes、reportsの報告生成、seer_future_bridge.prepare_game、取得/公開生成、Progress、今回の共通flowは残す。

exact.solve/reports.solve_reportsは旧方針の評価器でもあるため、無条件に新モデルの高速経路として流用しない。Aと一致した入力範囲だけを検証して採用する。Aのexchangeable_valueは既に条件付きの高速経路として残す。不要な互換exportは参照検索後に整理できるが、今回の移行仕様の不足を解消する作業とは別。

## 後続の承認範囲と実装順

上記比較と不足点の整理後、ユーザーはモデルAへの全体側統合も今回の整理で進める方向を承認した。この区切りは旧値不変で保存し、次段階では理由のある数値変更を許容する。新旧のUI選択肢や隠れfallbackは追加しない。新しい仕様判断と公開反映は別途確認する。

1. 公開用A評価facadeと期限内評価を追加し、まだ画面を切り替えず数値/対応範囲/予算を比較。夜の全体対象比較の条件付けを具体化して確認する。情報所有者の入力を公開・役本人・狼仲間に分け、秘密が公開ranking/cacheへ入らない契約をテストする。
2. BoardOverview、Tableの最終値/期限内値、累積とpreview/API再描画を同じfacadeへ移す。Board/戦略/公開履歴/私的履歴ごとのcache依存を明文化し、公開policyのcacheと閲覧者のpayoff cacheを分け、古い応答排除を維持する。CO/all以外を黙って旧へ落とさず不足分を補う。
3. 全設定/配役と9人の予算計測で縮退がないことを確認。同値保証できた圧縮高速経路を残し、呼出しがなくなった旧評価ループと互換exportを削除する。旧値fixtureは移行差の証拠として残す。新役職の追加部品と情報契約を開発メモにまとめる。

次段階の合格条件は一つの画面内の値の意味が揃うこと、既存対応範囲を維持すること、予算内の完全値または明示Pendingのみを返すこと、秘密非漏洩・同率・置換・戻る・遅延応答回帰の成功。性能不足が出た場合は、未対応化を隠さず具体的な盤面と実測を報告する。
