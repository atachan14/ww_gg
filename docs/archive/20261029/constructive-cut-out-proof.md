# 切り出し型：イベント構築による更新保証の小試作

`ConstructiveCutOutGroups` を独立追加した。旧照合型・前段の生成元検証付き試作・通常factoryを残す。今回の新経路は、更新時にも生成元交換の検証を行わない。初期構築と閉じたイベント言語の規則から、そのまま保持してよい対称性の部分群を作る。4〜5人の小fixtureのみで、未来勝率・7人・公開への接続は行っていない。

## 初期保証と引継ぎ

初期法則は、全ラベル付き配役の均等分布と、既存の均等な初日取得規則から構築する。任意の配役法則や入力関数に「対称」と宣言する入口はない。初期のS_n作用は、完全な配役・取得履歴・質量を同時に交換しても保存される。

各既存ブロックには、その内部の全交換が既存の完全共同分布・履歴・視点を保存するという保証がある。新イベントについて下表の区分を作り、**既存ブロックとの共通部分へ切り出すだけ**にする。新しい群を発見・再結合せず、過去の交換を再検証しない。各区分内の交換がイベントの操作と可換なので、条件付け後も保証が引き継がれる。

これは「同色だから同じ」という推論ではない。閉じたイベントごとの十分条件を実装し、その条件だけを使っている。一般の関係グラフの同型判定や最大対称群の発見は行わない。

| イベント | 今回保持する区分 | 保証の理由と限界 |
|---|---|---|
| 明示された同時CO | 同じCO役職を割り当てる位置の集合／今回変更しない集合 | 各集合内の交換はCO割当写像を保存する。既存の固定ClaimPolicyによる支持フィルタは役職名・人数・COに依存し番号に依存しない。別の時点のCOは別イベントとして順に処理する |
| 初日占い報告 | 全報告対象を各々固定。その対象以外の報告元は、同じ固定対象・色・取得枠の集合／今回無関係な集合 | 対象固定により報告元交換は同じ真占い支持条件を交換するだけ。明示的な同時バッチの条件の積を保存する。報告元が対象でもある場合はその位置も固定し、対称性を発見し直さない |
| 死亡位置の記録 | 今回死亡した集合／それ以外 | 同じ集合内の交換は生存集合からの除去を保存する。これは外生の死亡記録のみで、襲撃/処刑尤度や夜の物理枝を生成する保証ではない |
| 単独本人の役職 | 本人位置を固定／その他 | 本人の役職支持条件を保存する。公開法則を本人法則で置き換えない |
| 本人の取得結果 | 本人と対象を各々固定／その他 | 完全な取得記録の条件を保存する。他人の取得内容を推測して行動を決めない |
| 選択位置の記録 | 参照する全actor/targetを各々固定／その他 | 入力された名前付き関係を必ず保存する。方針の生成・最適化ではない。複雑な同時パターンでも細かく切る安全側の扱い |

既存の条件付きjoint法則を独立な役職率へ置き換えない。公開・本人の完全法則、基準上の支持質量、役職人数の共同組成、元の配役/秘密状態のmultiplicityは前段のcontextに保持する。今回も秘密法則そのものは明示列挙のまま。

## 証明できる範囲を超えた場合

- 対応するのは型検証された既存の `Observation` と、既知の対称な4/5人・狼1占1狩0・霊0/1・均等方針の基準のみ。任意関数、任意の入力法則、新しい遷移、max等へ自動適用しない。理由付きUnsupportedを維持し、旧照合型へ黙って戻らない。
- 報告は既存小試作どおりDay1昼・取得枠1。取得なし規則からの初日報告や、未知の報告生成確率、複数夜、GJは追加しない。
- 同じ相手への同じ白報告ならP1/P2を同群に保てる。一方P1/P2の相互黒報告では、両者を対象として固定するので分かれる。旧検証付き試作はそこを交換可能と確認できるが、新経路はその探索を行わず共有不足を許す。
- 各行の比較は引き続き `(同じ完全context参照, 群番号)` のみ。別context同士の共通化や通常PlayerDataへの接続はまだない。

## 同時順・CCO・取消訂正

一つのObservationの行は、呼び出し側が**同時と明示した**unorderedな支持条件バッチ。プログラム内の別イベントは順序を保持する。現在のCOだけを見て過去の条件を消したり、後から二つのCOを同時扱いしたりはしない。filled等の既存条件をいつのCOスナップショットへ適用するかで法則が変わり得ることを回帰検証する。

ゲーム内の未決の同時イベント順やCCOタイミングを新しく定めたわけではない。アプリ履歴からこのプログラムへの自動変換、未決のバッチ配置の推測、CO前後の公開生成ルールは未実装。明示済みの小プログラムだけを受ける。取消・訂正はactive_programを明示して基準から再構築し、再結合もその再構築で取り戻す。

## 残る費用を分離して記録

初期生成時間、更新全体、イベント処理、法則フィルタ/正規化、群の切り出し、支持質量の基準法則走査、役職率作成を計時する。更新全体はイベント・切り出し・支持質量を含み、イベント時間は法則条件付けを含むので二重加算しない。正規化等のcounterは入力仮説数で、内部の検証を含む全ループの厳密な走査回数ではない。

新経路は群の更新に過去イベントの対称性走査を使わない。ただし履歴の保存（tuple追加）と報告枠の重複確認は残る。`symmetry_history_rows_read` と `report_duplicate_history_rows_read` を区別する。完全joint法則の正規化・支持質量の確認にも依然として明示列挙の費用がある。この費用をキー構築の時間へ隠さない。

## 同じ意味・時機の複数actorを一括で切り出す案

同じ元群のactorが、同じsemantic event batchに含まれるなら、一人ずつsingletonにしてから結合し直す必要はない。今回のCO同役職集合、または同じ固定対象・色・取得枠を持つ報告元集合が、その限定実装にあたる。P1/P2同時占CO→両者が同じP3白、という小fixtureでは `{P1,P2}` を一つの切り出し群として維持する。7人にも同じ論証を検討できるが、実装の人数ガードは4/5のまま。

ただし、同じ白報告だけを根拠に別の元群を結合しない。他役の公開、被報告関係、本人条件、過去行動や設定済み方針によって片側だけが区別されていれば、継承した別ブロックを維持する。公開の共同秘密法則における交換不変性が必要であり、実際の秘密値を双方同じと仮定するわけではない。

現在のbatch入口は `Observation(kind, rows, day, phase)`。同じ種類の明示同時行だけを扱い、各イベントのゲーム時機とプログラム順は保持する。UI入力時刻は根拠にしない。複数種類のイベントを一つのゲーム時機に束ねる一般schema、CCO判定時点、公開時機とログ順の対応はまだ決めず、自動変換しない。

実装順は、今回の同対象・同色・同取得/公開時機という限定集合の保証を保持し、次にアプリ側の既存ゲーム時機/ログとの対応と明示batchの契約を決め、その後に種類を跨ぐイベントや人数拡張を個別に検証する。全一般グラフの同型探索や、既存順序を同時に読み替える実装は加えていない。
