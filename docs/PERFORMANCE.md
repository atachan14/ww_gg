新しい定義と [scope.md](redesign/scope.md) の戦略で、`wwcore/` を計った([redesign/core-v07.md](redesign/core-v07.md))。下の「基準にしてきた重いケース」と同じ公開情報だが、定義が違うので時間も値も単純には比べられない。再現は `dev_previews/benchmark_wwcore.py`(計測は別プロセスの cold、同じ PC。上限を付けて1つずつ実行)。

### 分かったこと

- **一致グループは、公開の記録に名前が多いケースでは今のところ効いていない。** 名前を振り直すだけの素朴な数え上げのほうが、7人でも 8人でも速い。報告で名前が出るとグループがすぐ崩れるので、人数で持つ得が小さく、切り出しと番号の振り直しの手間のほうが大きい。全員潜伏のケース(9人で 7.3秒)では効いている。
- **重いのは Board の数。** 偽の報告の組み合わせで、Board が記録ごとに別になる。7人のプロファイルでは、番号の振り直し(`canonical_order`)・切り出し(`split`)・分数の計算が大きい。
- **9人の見込みは、このままではない。** 公開の CO・報告がある 9人は 10分で終わらない。全員潜伏の 9人は軽いので、配役の数そのものではなく、偽の報告が作る枝が問題。

### 次に試す案(未実施)

1. Board の使い回しの鍵を、記録全部から「その先に効くものだけ」に変える。生死、CO、報告済みの相手、白黒の数、役職率が同じなら、その先は同じ。効果は最も大きい見込み。
2. 死んだ人の役職を、その先の計算の状態からは消す(今の処刑先の結果と昨夜の占い先だけ残す)。
3. 偽の報告の候補を、対象の立場ごとにまとめる。

## 時間がかかっているところ(2026-10-26〜27 の計測)

計測の中身は、状態を作る処理(`Board`・`TrueScanState`・`Hypothesis` の生成と検証)、正規化(`normalize`)、ハッシュと等価比較、分数の計算に集中していた。

| 処理 | 呼び出し回数 |
|---|---|
| `Board` の生成 | 約27万 |
| `normalize` | 約15万 |
| `TrueScanState` の生成 | 約17万 |
| `Hypothesis` の生成 | 約34万 |
| `dataclasses.replace` | 約100万 |
| `hash` | 約1300万〜2100万 |
| `Fraction` の加算 | 約310万 |

旧 docs の見立てでは、ハッシュ・等価比較・厳密な計算・記録の検証の多くは「必要な作業」。ほぼ全部が公開ラベルのためだけに呼ばれていた `transport_source`(約8.5万回)は、取り除ける作業として特定された。

## 構造についての判断(2026-10-17)

細かい軽量化は一区切りとした。**今の構造のまま一般の9人まで伸ばせる根拠も、今すぐ全面的に作り直す根拠もない。** 次は、目標とする9人の入力と、必要な出力を固定してから、構造の点検と計測をする、という判断だった。

## 目標(2026-10-29 ユーザー確認)

- **目標のケース**: 上の7人のケースを基準にする。これより重い状況は、具体的には確認していない。
- **目標の時間**: 早ければ早いほどよい。
- **厳密さ**: 打ち切り・近似をしない原則は維持する。表示を段階的にする(先に役職率、後から勝率)などの工夫は使ってよい。
- **目標の人数**: v1 の目標は9人。将来は20人以上も目指したいが、今のところ可能な見込みはない。
- **順番**: 先に v0.6 で区切りを付け、その後に要件の整理と設計の見直しをしてから、重さに取り組む([STATUS.md](STATUS.md) の「今後の進め方」)。
