# 重さの問題

**今いちばん解決したい問題。** 配役によっては7人で計算資源(時間・作業量の上限)が尽き、結果が「未計算」になる。(2026-10-29 ユーザーの発言)

この文書は、重さの改善を始めるための出発点。これまでの計測と、試した改善の記録を、archive の各記録からまとめた。数値はそれぞれの日付・コミット・環境での記録で、今のコードを測り直したものではない。

## 上限

- アプリの上限は 270秒 / 400万 work。Vercel の関数の上限は300秒([spec/hosting.md](spec/hosting.md))。
- 上限に達したら「未計算」と表示する。打ち切りや近似で値を出すことはしない([PURPOSE.md](PURPOSE.md))。

## 基準にしてきた重いケース

**7人: 市民3・霊能1・占い師1・人狼2、すべて max、勝ち確定で打ち切り On。P1 と P2 が占いCOして、2人とも Day1 に P3 を白と公開。P3 が霊能CO。** Tree の初期の要求の順番も固定。全体の勝率 89/224。再現用のスクリプトは `dev_previews/profile_navigation_update.py`。

## 時間がかかっているところ(2026-10-26〜27 の計測)

計測の中身は、状態を作る処理(`Board`・`TrueScanState`・`Hypothesis` の生成と検証)、正規化(`normalize`)、ハッシュと等価比較、分数の計算に集中していた。

| 処理 | 呼び出し回数 |
|---|---|
| `Board` の生成 | 約27万 |
| `normalize` | 約15万 |
| `TrueScanState` の生成 | 約17万 |
| `Hypothesis` の生成 | 約34万 |
| `dataclasses.replace` | 約100万 |
| `hash` | 約1300万〜2100万 |

旧 docs の見立てでは、ハッシュ・等価比較・厳密な計算・記録の検証の多くは「必要な作業」。ほぼ全部が公開ラベルのためだけに呼ばれていた `transport_source`(約8.5万回)は、取り除ける作業として特定された。

## 構造についての判断(2026-10-17)

細かい軽量化は一区切りとした。**今の構造のまま一般の9人まで伸ばせる根拠も、今すぐ全面的に作り直す根拠もない。** 次は、目標とする9人の入力と、必要な出力を固定してから、構造の点検と計測をする、という判断だった。

## 改善を始める前に決めること

- 「重い」とする具体的な配役・ルール・戦略・盤面(目標のケースの一覧)。
- 目標の時間(例: 上限の270秒に収める、普段の操作で何秒以内)。
- 厳密さの原則(打ち切り・近似をしない)は維持する前提か。表示を段階的にする(先に役職率、後から勝率)などの工夫で許される範囲。

これらは [QUESTIONS.md](QUESTIONS.md) に入れている。
